# Agent 应用开发学习路线与面试计划

适合对象：有 C++ 和图像处理背景，准备转向企业 Agent 应用开发、AI 产品工程或多模态应用开发。目标周期为 12–16 周，默认每周投入 15–20 小时。12 周约 180–240 小时，16 周约 240–320 小时；如果每周只有 8–10 小时，应延长周期或减少项目功能。

学习目标是独立完成一个可演示、可部署、可评估的企业业务应用，理解关键代码，并能解释业务价值、技术选择和失败处理。完成路线后具备准备相关面试的作品与知识基础；岗位要求的实际工作年限和真实生产经验仍需如实说明。

建议主项目为「电商售后异常处理工作台」，第一条流程聚焦商品破损申请补发。前三个月完成这条流程与求职材料，第四个月根据面试反馈做强化。学习按项目问题推进，课程用作参考，不以看完视频数计算进度。

## 路线速查

| 阶段 | 必须学会 | 项目结果 | 求职进度 |
| --- | --- | --- | --- |
| 第 1–2 周 | Python 应用开发、HTTP、模型调用、结构化输出 | 文本工单转结构化信息，并查询模拟订单 | 能解释一次模型请求和一次工具调用 |
| 第 3–4 周 | Tool Calling、RAG、检索评估 | 根据订单和售后规则生成带引用的建议 | 开始积累项目问答和错误案例 |
| 第 5–6 周 | 工作流、状态持久化、人工审批、幂等 | 审批后执行模拟补发，支持中断与恢复 | 能画流程并解释为什么这样设计 |
| 第 7–8 周 | 图片处理、多模态、前后端衔接 | 图片证据、工单页面、处理轨迹可演示 | 开始试投，收集岗位和面试反馈 |
| 第 9–10 周 | 自动评估、异常处理、成本与延迟 | 基线对比、评估报告、权限与故障案例 | 简历使用真实测量结果 |
| 第 11–12 周 | 部署、技术表达、基础题复习 | 可复现项目、演示视频、技术说明 | 正式投递和模拟面试 |
| 第 13–16 周 | 真实试用、领域扩展、专项补短板 | 一个相邻场景与一次有证据的迭代 | 按目标岗位调整展示重点 |

学习优先顺序：模型与工具调用 → 业务数据与规则检索 → 状态与人工审批 → 多模态 → 评估与工程完善。多 Agent、A2A、模型微调和大型平台放到具体需求出现之后。

## 需要掌握的知识及掌握程度

“能解释”指能用自己的例子说明作用与限制；“能独立实现”指离开教程能完成核心功能、定位错误；“能比较”指能用同一组数据说明不同方案的取舍。

| 内容 | 必须掌握的范围 | 达到什么程度 |
| --- | --- | --- |
| Python 与后端 | 类型标注、异常、文件与 JSON、包管理、async/await、HTTP API、输入校验 | 独立实现一个带超时、错误返回和日志的接口；能解释阻塞代码对异步服务的影响 |
| LLM 基础 | token、上下文窗口、消息角色、采样、流式输出、幻觉、Embedding、模型选择 | 能解释参数影响，读取用量，区分模型能力与应用问题 |
| Prompt 与输出 | 任务边界、输入分隔、示例、JSON Schema、Pydantic 校验、版本管理 | 输出非法或字段缺失时能发现并处理；schema 合法后仍校验业务含义 |
| Tool Calling | 工具描述、参数 schema、模型提出调用、应用执行、结果回传、循环终止 | 先独立实现一次完整调用循环，支持缺参、工具失败和调用上限 |
| 工作流与 Agent | 固定流程、动态工具选择、ReAct 思路、路由、状态机、停止条件 | 能说明每一步由规则、模型或人工负责；理解 Agent 循环不保证正确结果 |
| RAG | 文档清洗、分块、元数据、Embedding、向量检索、关键词检索、混合召回、重排、引用 | 完成基础检索，并区分没检索到、检索错、生成没用好证据三种失败 |
| 上下文与记忆 | 任务状态、对话历史、检索结果、历史摘要、长期偏好 | 控制上下文长度与费用；区分业务数据库、会话状态和长期记忆 |
| MCP 与 Skills | MCP 的 Host/Client/Server、工具发现与调用；Skill 中的操作流程与参考材料 | 将一个订单查询工具接成 MCP；能比较直接函数、HTTP API 和 MCP 的用途 |
| 工程可靠性 | 超时、有限重试、错误分类、幂等、事务、检查点、恢复、人工接管 | 重试和恢复时不重复创建业务单据；人工审批后重新校验业务状态 |
| 企业权限 | 身份校验、角色权限、数据归属、读写分离、审计、敏感信息处理 | 后端决定能查哪些订单、能执行哪些动作；请求中的商户 ID 不能直接充当权限证明 |
| 评估与观测 | 数据集、基线、错误分类、运行轨迹、版本比较、耗时和费用 | 用脚本批量运行，定位失败发生在哪一步，复现一次具体失败 |
| 多模态 | 图像质量、OCR 与视觉模型边界、图片坐标与证据、模糊与不确定情况 | 对图片给出可核对的观察；不把模型生成的自信表述当作可靠置信度 |
| 产品与业务 | 用户、流程、输入输出、处理边界、验收标准、人工耗时 | 能解释用户如何完成任务、为什么愿意使用，以及如何验证价值 |

LLM 原理学到能解释 token、Embedding、Transformer 注意力和自回归生成即可。训练损失、预训练数据治理、分布式训练属于后续方向。应用开发面试仍需要基本原理，但当前时间应优先投入工具、检索、流程、工程和评估。

## 项目范围与技术选择

目标用户为售后客服或运营。第一版输入为客户描述、订单号和商品照片，系统查询订单与物流、检查图片质量、查售后规则，输出处理建议、依据、缺失信息和需要人工确认的事项。客服批准后调用模拟补发接口，生成处理记录。

处理顺序：提交工单 → 校验身份与必填信息 → 查询订单和物流 → 图片观察与规则检索 → 生成建议 → 确定性规则校验 → 人工审批 → 再次检查订单与审批状态 → 执行模拟补发 → 保存审计记录。缺信息进入补充材料状态，接口暂时失败进入有限重试，无法判断进入人工接管。

第一版交付以下功能：

1. 上传工单与图片，展示订单信息和当前处理状态。
2. 查询订单、物流、售后政策的 3–5 个工具；订单状态走业务 API，政策解释走检索。
3. 返回结构化处理建议，能点击查看引用的政策版本、原文片段和图片证据。
4. 审批人可以同意、修改或驳回；审批状态持久保存。
5. 模拟补发工具使用幂等键，同一审批不能重复执行；失败后能查询动作是否已成功。
6. 能回看输入、工具参数、输出、错误、版本、耗时与用量。
7. 提供批量评估脚本、样本说明和演示说明。

图片能力从“能否看清、能观察到什么、是否需要补图”起步。照片可支持售后判断，但不能单凭图片证明责任归属或欺诈。若要输出破损框，必须验证定位和坐标转换；没有可靠定位时展示原图与文字观察即可。

建议使用 Python、FastAPI、Pydantic、一个模型 SDK、LangGraph 和 PostgreSQL。先用原生 SDK 理解调用过程，再引入框架；LangChain 用于需要的模型、工具或检索组件。LangGraph 可组合确定性步骤和模型步骤，并管理共享状态与人工介入，不强制依赖 LangChain。[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

前两周可用 SQLite 快速启动，随后在学习事务、索引与并发时切到 PostgreSQL。向量存储只选一种；已有 PostgreSQL 时可评估 pgvector。前端只实现工单列表、详情、审批和轨迹，使用熟悉的方式完成。Redis 和任务队列在出现后台长任务、并发或跨进程处理需求时加入。

保留 C++ 优势：把现有图像质量检测、裁剪或预处理模块包装成工具，通过进程或 API 接入；避免为了组合技术栈额外编写没有作用的视觉模块。8GB 显存、16GB 内存的机器可以先用模型 API 做主链路，本地处理图片与业务服务；训练和同时部署多个大模型不列入前 12 周交付范围。

## 现有教程的选学顺序

课程范围依据已有的[六门课程总览与逐章导读](./六门课程总览与逐章导读.md)。字幕中的 API 名称和代码细节仍需核对原视频，实际实现采用锁定版本的依赖与对应官方文档。

| 用途 | 课程范围 | 使用方法 |
| --- | --- | --- |
| 理解概念 | 小哲第 1–10、27–30、31–60、63–79 节 | 每次选与当前问题有关的短节，写一个自己的项目例子 |
| 学模型和工具组件 | LangChain 第 21–70 节 | 第 21–30 节按 Python 熟练度补；31–60 节重点动手，61–70 节用来处理失败 |
| 学检索 | LangChain 第 101–120 节 | 完成加载、分块、检索和问答后，自己补上检索评估与政策版本过滤 |
| 做主项目参考 | MCP+A2A 课程第 3、4、5、7、9、10、16 章 | 取用工具、结构化数据、API、状态、人机交互；同一能力只完整实现一遍 |
| 做页面和部署 | MCP+A2A 第 17–19 章选看 | 只学习工单页面所需的附件、事件、接口和部署内容 |
| 补另一种实现 | 编程智能体第 4–6、11–12、15–17 章 | 主线卡住时查阅，重点看知识库、业务工具和图流程 |
| 参考产品交互 | Hermes 第 11–30 节选看 | 观察任务状态、工具轨迹与技能使用，不要求迁移到其框架 |
| Java 岗位补充 | SpringAI 第 3、4、6、7、10 章 | 确定投递 Java/Spring 岗位后再补，首个项目保持一个主后端栈 |

暂时后置 MCP+A2A 的远程 Agent 协作、大型沙箱平台和分布式服务。MCP 必须理解并完成一个工具接入，A2A 先理解其解决独立 Agent 服务互通的问题。多 Agent 先能解释任务分工、上下文隔离、额外成本和失败传播；只有单 Agent 的测量结果暴露具体问题时，再做对比实验。

之前关注的 CMU 11-768 可以作为后续原理补充。前 12 周先围绕当前缺口查材料，不再增加一门需要从头看完的主课。

## 第 1 至 4 周建立调用和检索基础

| 周次 | 学习与课程 | 当周任务 | 完成标准 |
| --- | --- | --- | --- |
| 第 1 周 | Python 类型、异常、JSON、HTTP；小哲 1–10；LangChain 21–30 按需 | 建项目、环境和 Git；写一页业务流程；整理 20 个开发工单；调用模型提取订单号和问题类型 | 能独立启动程序、读取配置、校验输出，解释一次请求的数据流 |
| 第 2 周 | Prompt、Pydantic、Tool Calling；LangChain 31–60；MCP+A2A 4、9、10 章选看 | 实现订单和物流查询；先用原生 SDK 写调用循环，再接 FastAPI | 处理查无订单、缺订单号、非法参数、工具超时；限制调用次数 |
| 第 3 周 | 文档清洗、分块、Embedding、检索；小哲 63–79；LangChain 101–120 | 编写一套明确标注为模拟的售后政策，保存政策 ID、版本、适用商户；生成带引用建议 | 正确引用支持结论的原文，没找到依据时请求补充或转人工 |
| 第 4 周 | 关键词与向量检索、元数据过滤、基线评估；编程智能体 11–12 章按需 | 构造含相似规则、旧版规则、无答案的问题；对比关键词和向量检索，按结果决定是否混合或重排 | 能分开报告检索命中和最终建议质量，举出至少 3 个失败原因 |

第 4 周结束，能演示一条文本工单流程：收到问题、查询订单、检索政策、展示建议。先保证订单金额、状态和时间等字段来自确定的业务数据。

数据集逐步建立为 30 条开发样本、30 条回归样本、20 条最终留出样本。前期不足 80 条时按比例扩展，优先覆盖不同错误类型。开发样本用于调整 Prompt；回归集反复测版本；最终留出集在第 11 周才评估，避免把反复调过的样本当成未知样本。政策、样本和标准答案都要版本化。

## 第 5 至 8 周完成业务流程和多模态页面

| 周次 | 学习与课程 | 当周任务 | 完成标准 |
| --- | --- | --- | --- |
| 第 5 周 | 图工作流、状态、条件分支；编程智能体 16–17 章；MCP+A2A 16 章 | 将现有流程改为明确状态，加入补材料、人工接管和停止状态；保存检查点 | 能中断、重启服务、读取任务状态，解释哪些节点会再次执行 |
| 第 6 周 | 审批、幂等、事务、MCP；MCP+A2A 7、10、16 章 | 实现审批和模拟补发；订单查询接一个 MCP Server；写接口契约 | 未审批不能执行，重复审批不重复补发；知道 MCP 不等于业务授权 |
| 第 7 周 | 视觉模型、图片质量与证据；MCP+A2A 第 3、4 章图像部分 | 接图片观察和一个有实际作用的图像工具；加入模糊、反光、无关图片样本 | 不清楚时要求补图；保留原图和处理版本；比较加视觉前后的结果 |
| 第 8 周 | 前后端接口、异步处理、状态展示；MCP+A2A 17–18 章选看 | 做工单列表、详情、规则引用、审批按钮、任务状态和错误提示 | 他人按照说明能完成一次处理；可演示正常、缺材料、工具失败三种情况 |

人工暂停必须配合持久化状态、稳定任务标识和恢复逻辑；恢复过程中的重复执行也要纳入设计。[LangGraph 人工中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

检查点恢复仅恢复程序状态。已经提交到外部系统的动作，需要查询执行结果或调用业务补偿接口；重新加载旧检查点不会撤销补发或退款。这个区别要能在面试中解释。

第 8 周可以开始试投：至少准备可运行版本、简短说明和 3 分钟演示。把面试暴露的问题加入后续学习清单；不要为了等待全部功能完成而推迟求职反馈。

## 第 9 至 12 周形成工程证据和面试材料

| 周次 | 学习重点 | 当周任务 | 完成标准 |
| --- | --- | --- | --- |
| 第 9 周 | 评估、运行轨迹、Prompt 与模型版本 | 跑批量评估；保存版本、样本 ID、工具结果、耗时与 token；做基线比较 | 同一个失败案例可复现，能指出优化解决了哪类错误以及代价 |
| 第 10 周 | 权限、提示注入、超时、重试、并发和幂等 | 验证用户不能查询其他商户订单；知识材料中的指令不改变工具权限；模拟接口超时与重复请求 | 后端检查权限；有限重试不会重复动作；异常能交给人工接管 |
| 第 11 周 | Docker、环境变量、数据库迁移、回归与最终留出评估 | 完成部署说明，换环境启动；跑最终留出集；请 1–3 人试用并收集反馈 | 新环境可运行，结果可核对；说清试用者和样本的适用范围 |
| 第 12 周 | 项目讲解、基础题、系统设计和投递 | 完成 README、流程图、评估报告、演示视频和简历；做两次模拟面试 | 能讲 3 分钟与 10 分钟两个版本；解释关键代码和至少两个失败案例 |

对版本做离线数据集比较，把实际失败加入回归集，是可持续迭代的基本方法。可先用 JSONL、Python 脚本和 CSV 实现，再按需要接评估平台。[LangSmith 评估文档](https://docs.langchain.com/langsmith/evaluation)

## 第 13 至 16 周按岗位强化

| 周次 | 建议任务 | 完成标准 |
| --- | --- | --- |
| 第 13 周 | 依据试用或面试反馈修一个最明显的问题 | 保留一例修复前后的对比并跑原有回归集；暂时拿不到真实业务用户时，记录为模拟场景试用 |
| 第 14 周 | 增加一个相邻流程，例如错发商品处理 | 至少增加 5 条新流程样本并通过原流程回归；列出复用的审批、日志和工具，以及必须新增的规则 |
| 第 15 周 | 根据主投岗位补一个专项 | 电商岗画清订单/库存关系并演示一次查询；多模态岗提交视觉错误分析；工程岗记录一次并发与恢复实验；产品岗完成一次需求访谈或可用性试用。选一项完成 |
| 第 16 周 | 集中面试、修缺口、整理项目故事 | 完成两次模拟面试并关闭其中两个主要问题，更新简历与演示；保留可展示的稳定版本 |

若只有三个月，保留第 1–12 周的完整主流程。减少视觉定位、复杂前端、混合检索和第二场景的深度，优先保住工具调用、引用、审批、幂等、评估、部署和基础题。

## 每天和每周怎么学

每周以 18 小时为例：项目实现 8 小时、课程与官方文档 4 小时、Python/数据库/网络基础 3 小时、面试表达与练习 2 小时、复盘和计划 1 小时。早期把面试练习用于口述所学，后期逐步增加模拟面试时间。

一次 90 分钟学习可以这样安排：

1. 用 10 分钟写出一个具体问题，例如“补发接口超时后能不能重试”。
2. 用 20 分钟读字幕或看相关片段，找到实现思路；界面操作和代码调试再看视频。
3. 用 40 分钟在自己的项目中实现，主动造一个失败输入。
4. 用 15 分钟记录输入、预期、实际结果和原因，保存一条回归用例。
5. 用 5 分钟口述这个设计；讲不清的部分列为下一次学习任务。

笔记每个主题只保留四项：解决什么问题、在项目中怎样实现、失败过什么、面试怎样解释。每周提交一个可运行版本，留一段演示和一页简短复盘。

用 AI 编程工具时，先自己写输入输出、状态和验收条件，再让工具补代码。对工具循环、检索、审批和幂等这些核心逻辑，应能自己改需求、定位故障和解释调用顺序。重复的样板代码可以交给工具完成。

控制学习和开发成本：把固定工具返回值保存为测试夹具；只测改动影响的样本；本地校验 JSON 和业务规则后再做模型评分；只有发布里程碑才跑完整集。缓存读取和实时模型调用分开记录，避免将缓存结果的费用、速度算成模型本身表现。

## 评估应该记录什么

先做“模型直接阅读工单并生成建议”的基线，再依次比较增加订单工具、政策检索和视觉证据的结果。模型、数据集、采样参数和评判口径保持可比，一次只改一个主要因素；改动很多时明确记录，避免误归因。

| 指标 | 建议口径 | 注意的业务含义 |
| --- | --- | --- |
| 检索命中 | 有标准依据的问题中，正确政策片段是否出现在前 k 条结果 | 先判断材料有没有被找对 |
| 引用正确 | 引用片段是否实际支持建议，且政策版本适用 | 附上链接不等于有证据 |
| 建议质量 | 按固定标准判为可接受的建议数 / 可评样本数 | 人工修改后通过和原始输出通过分开统计 |
| 自动处理覆盖 | 无人工修改即可达到验收要求的样本比例 | 与质量一起看，全部转人工不能算自动处理成功 |
| 危险动作 | 未授权、未审批或重复写入的次数 | 在明确测试集内单独报告，不能靠平均分掩盖 |
| 性能与费用 | 端到端耗时分布、失败率、每任务用量与估算费用 | 标明样本数、并发、模型、缓存和环境；人工等待时间另列 |
| 视觉表现 | 观察正确、误判、漏判、要求补图的数量 | 按模糊、反光、无关图片等类型拆分 |

输出合法性、订单 ID、权限、金额边界、重复动作等用代码检查；处理建议和视觉观察用人工标准评分。可以用模型辅助评价，但需要人工抽查，不能只让同一个模型评价自己。

以下是本项目建议的发布门槛，不是行业统一标准：测试集中的越权、未审批执行和重复补发均不允许通过；异常时必须有明确结果或人工接管入口；建议质量与覆盖率在做完基线后确定数值目标。报告同时保留正确数、总数和错误案例，小样本百分比不代替实际业务验证。

## 面试基础要同步准备

每周做 3 次、每次约 45–60 分钟的基础练习，优先覆盖目标岗位真正需要的内容。

| 方向 | 高频范围 | 练习方式 |
| --- | --- | --- |
| Python | 可变与不可变、引用、异常、生成器、装饰器、上下文管理器、类型标注、异步 | 写一个带超时的并发查询，解释何处使用线程、进程或异步；理解 GIL 的常见限制 |
| SQL 与数据库 | JOIN、聚合、索引、事务、隔离级别、唯一约束、幂等写入 | 用订单与工单表写查询，设计避免重复补发的约束 |
| HTTP 与后端 | 请求响应、状态码、鉴权、SSE、超时、限流、分页 | 说明一次工单创建和状态更新的全过程，解释断线后如何恢复 |
| Linux 与工程 | 进程、端口、日志、环境变量、Git、依赖锁定、Docker | 自己部署和排查一次连接失败或配置错误 |
| 数据结构 | 哈希表、链表、栈队列、二分、堆、树的遍历、复杂度 | 每周完成少量典型题并口述思路，投递前按目标岗位加练 |
| C++ 与视觉 | 自己实际使用过的资源管理、智能指针、并发、图像处理方法 | 能深入解释已有优势；简历写了的内容必须经得起追问 |

## 核心面试问题与回答要点

| 问题 | 回答中至少包含 |
| --- | --- |
| Agent、工作流和普通模型调用有什么区别 | 控制流程由谁决定；以本项目一个固定步骤和一个模型选工具步骤举例 |
| 为什么不全部交给模型决策 | 订单权限、审批、金额、幂等由确定性代码约束；模型负责适合语言和视觉判断的部分 |
| Tool Calling 的实际执行过程是什么 | 模型返回工具请求，应用校验与执行，结果回传，模型继续；不是模型直接操作数据库 |
| 结构化输出能解决幻觉吗 | 能约束格式和类型；内容正确性仍需要证据和业务校验 |
| RAG 没效果如何定位 | 查原文、分块、过滤、召回、排序、上下文和最终引用，指出自己遇到过哪一类 |
| 为什么用 RAG，不直接微调 | 政策更新、证据追溯与模型行为学习的不同目标；以当前数据量和更新频率解释取舍 |
| 为什么有向量检索还考虑关键词 | 订单号、商品型号、专有词和语义表达的检索差异；提供实际样本比较 |
| chunk 大小和 top k 怎么选 | 根据文档结构、问题类型、召回、上下文费用和评估结果调整，避免只背固定数值 |
| 上下文、状态和长期记忆有何不同 | 本次模型可见内容、任务执行事实、跨任务保存信息的边界与生命周期 |
| MCP、函数调用和 HTTP API 什么关系 | 模型调用接口、应用工具实现、标准化接入层各自的职责；MCP 不替代权限校验 |
| Skills 和 MCP 有什么区别 | 前者可提供任务流程和参考材料，后者规范工具/数据接入；流程说明也需要执行权限配合 |
| 为什么使用 LangGraph | 状态、分支、人工暂停和恢复的实际需要；哪些部分用普通函数实现就足够 |
| 审批后服务重启怎么办 | 持久化任务与审批，稳定标识恢复，执行前校验有效性，动作使用幂等键 |
| 超时后怎么防止重复补发 | 超时不代表对方未执行；查询执行结果、幂等键、唯一约束和状态迁移 |
| 检查点回滚能撤销退款吗 | 不能；外部动作需要业务补偿或人工处理，与程序状态恢复分开 |
| 如何应对知识库中的恶意指令 | 材料作为不可信数据；后端校验身份、资源和工具权限，不能靠 Prompt 代替授权 |
| 多 Agent 一定更好吗 | 分工与隔离收益、成本、延迟、通信和错误传播；用可测问题决定是否采用 |
| 多模态相比纯文本改善了什么 | 展示相同样本的比较和错误分类；说明视觉不确定情况与需要人工判断的边界 |
| 怎么证明项目有效 | 固定数据、基线、评价标准、版本对比、失败案例、试用反馈和费用记录 |
| 降成本会怎么做 | 减少无用上下文和工具循环、缓存适用数据、规则前置、按任务选模型，并检查质量回归 |

每周从表中选 3–5 题，每题先讲 1 分钟，再用 3 分钟展开实际代码和失败案例。无法举项目例子的术语，回到项目补一个小实验。

## 求职展示材料

第 12 周应准备好：

- 一页业务说明：用户、原流程、痛点、输入输出、人工确认点、验收口径。
- 一个能启动的仓库：README、配置示例、依赖版本、模拟数据、启动和评估命令。
- 一张系统图和一张业务状态图，标出模型、工具、数据库与审批的边界。
- 一份评估报告：数据来源、样本分布、基线、版本、质量、费用、延迟和失败案例。
- 一段 3–5 分钟演示，包含正常处理、补材料或拒绝执行、故障恢复。
- 至少两篇简短技术记录，例如“如何避免重复补发”和“政策检索失败如何定位”。

3 分钟讲项目：业务问题约 30 秒，流程演示约 60 秒，关键设计约 60 秒，测量结果和限制约 30 秒。10 分钟版本增加架构、失败分析和取舍。涉及订单、支付或库存的模拟接口在材料中标明；试用、压测和真实生产上线分开描述。

简历可以使用以下句式，所有括号都在测量后填写：

“开发面向电商售后的多模态工单工作台，接入模拟订单与物流服务，结合政策检索生成带引用建议，实现人工审批、幂等执行及运行审计；在包含〔样本数〕条工单的评估集上，相比〔基线〕，〔指标〕由〔结果〕变化为〔结果〕，记录端到端耗时与单任务费用。”

面向 AI 应用开发岗，突出工具、状态、评估和部署；面向电商岗，突出订单数据、业务规则和异常处理；面向多模态岗，突出图像处理、视觉误差分析与证据；面向产品工程岗，突出需求到试用反馈的过程。纯产品经理岗位还会考查需求访谈、优先级和推进经验，项目作品可以补充这些证据。
