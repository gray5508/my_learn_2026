## 先定一个作品

主项目做「电商售后破损补发工作台」，面向客服审核员。输入客户描述、订单号和商品照片；查询**模拟**订单/物流数据和版本化售后政策；输出结构化建议、政策引用、照片观察与不确定项；由人工批准后调用**模拟**补发接口，保存状态与审计轨迹。先只处理一个商户、一类破损补发流程，缺材料、政策不适用或证据冲突时转人工。不得让模型直接决定订单归属、金额、审批或实际写入。

这仍是 Agent 应用：模型在受限工具中完成信息提取、证据整理和建议；业务流程、权限与写操作由程序控制。若固定步骤已经够用，就保持固定工作流，不为展示“多 Agent”而增加角色。第 13–16 周可把同一底座扩展到错发商品或企业内部申请审批。

**最小交付闭环：**提交工单 → 校验身份/输入 → 查订单和物流 → 检索适用政策 → 观察图片 → 生成带引用建议 → 确定性规则校验 → 人工审批 → 重新查业务状态 → 幂等模拟补发 → 保存审计。每个失败分支都要有明确的“补材料、重试或人工接管”结果。

## 可复现的开源参照与展示素材

## 技术与资源边界

- 主栈：Python、FastAPI、Pydantic、一个模型 SDK、SQLite 起步。政策库可先用文件 + 关键词检索；确有提升再选一个向量存储。LangGraph、PostgreSQL、Redis、队列均由项目复杂度触发。前端只需能完成客服流程。
- 8GB 显存、16GB 内存：主链路优先调用模型 API，本地运行 API、数据库、图片预处理和评估脚本；不把本地训练或同时运行多个大模型列为交付。记录模型与费用，固定测试数据减少重复调用。
- C++ 优势用在一个能测出价值的图像工具（例如模糊/曝光检测、裁剪或 OCR 前处理）。已有代码可经进程或轻量 API 调用；没有合适现成模块时先用 Python/OpenCV 实现并报告效果。视觉输出只写“观察到什么”，不能仅凭照片判定责任或欺诈。
- 真实客服资料、订单、照片应经授权与脱敏。前 12 周可全部使用自制/模拟数据，明确写在项目、简历与演示中。模型生成的“置信度”不是校准概率。
- 若用 LangGraph，按[官方持久化](https://docs.langchain.com/oss/python/langgraph/persistence)和[人工中断](https://docs.langchain.com/oss/python/langgraph/interrupts)实现稳定任务 ID、检查点和恢复。程序状态恢复不能撤销外部补发；副作用靠业务幂等键、结果查询和必要时人工补偿。

## 评估设计和完成标准

第 1 周写好样本字段和评分规则，再逐步扩充到约 40–60 条有代表性的模拟工单：开发集约 20–25，回归集约 15–25，最终留出集约 10–15。样本少时报告**分子/分母**和失败细节，不用小样本百分比暗示生产效果；留出集在第 11 周之前不调 Prompt。政策、图片、标准答案和模型版本均要可追踪。无真实业务用户时写“模拟评估”，不写“企业上线”或“真实提效”。

| 指标 | 口径与验收 |
| --- | --- |
| 检索 | 正确且适用的政策片段进入 top-k 的条数；旧版本误用单列。 |
| 引用/建议 | 引用原文确实支持结论的条数；原始建议可接受数、人工修改后可接受数分开。 |
| 安全动作 | 越权、未审批执行、重复补发分别计数；在专门构造的故障测试中应为 0。 |
| 图像 | 可见事实正确、误判、漏判、要求补图的条数，按模糊/反光/无关图拆分。 |
| 工程 | p50/p95 响应耗时、错误率、token 与估算费用；记录并发、缓存和环境，人工等待时间另列。 |

比较版本时保持数据、评分和模型参数尽量一致，每次只改一个主要因素。输出格式/权限/金额/重复写入用代码判定，图片与建议用人工标准抽查；可用模型辅助评分，但要记录人工分歧。第 12 周报告至少包含一张版本对比表、三类失败、改动收益与代价。

## 必备知识与面试准备

**必须能独立改动并解释：**Python 类型/异常/异步、HTTP/鉴权、Pydantic 校验、模型请求与工具调用循环、结构化输出、检索与引用、SQL/事务/唯一约束、状态/审批/幂等、日志与故障定位、容器启动。LLM 原理掌握 token、上下文、Embedding、注意力和自回归生成的用途与限制；训练算法、分布式训练、A2A、多 Agent 优化放后续。

**每周固定 2–3 小时面试练习：**一半讲项目，一半练 Python/SQL/HTTP/Linux/常见数据结构；保留 C++ 内存管理和图像处理的真实项目故事。每周选 3–5 个问题口述 1 分钟和 3 分钟版本，包括：为何用工作流/Agent、工具调用实际谁执行、RAG 错在检索还是生成、审批后重启如何恢复、超时后为何不能直接重试写入、MCP 与函数/API 的边界、图片比文本增加了什么、如何证明效果、哪些是模拟数据。每个答案都给自己的代码位置或失败样本，不靠术语堆砌。

简历只写已做且可复测的事实，可在第 12 周填入：“开发面向电商售后的图文工单工作台，接入模拟订单/物流和版本化政策检索，实现人工审批、幂等模拟补发与运行审计；在〔样本数〕条模拟工单上，〔指标〕从〔基线〕变为〔结果〕，单次耗时和费用为〔实测〕。”

**每周时间分配（18 小时示例）：**项目 9 小时，定向课程/官方文档 3 小时，Python/数据库/网络 3 小时，评估和面试表达 2 小时，复盘 1 小时。每周只问：本周新增了哪条可演示能力？新增哪个失败样本？下周最大的一个阻碍是什么？实际完成情况写入[学习进度](学习进度.md)。
